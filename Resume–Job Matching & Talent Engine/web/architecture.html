Algorithmic Selection Rationale: A naive engineering approach would attempt a brute-force scan or monolithic scoring function for all operations. Talent Engine demonstrates rigorous problem decomposition:
  • String Search requires avoiding redundant re-comparisons, which is solved by KMP prefix function $\pi$ and Rabin-Karp $O(1)$ rolling hash.
  • Typo Tolerance cannot use naive equality; it requires optimal substructure via Levenshtein & Damerau Dynamic Programming.
  • Rapid Talent Search demands avoiding $O(N)$ linear scans, achieved through an inverted index in $O(1)$ average time via HashMap buckets.
  • Bijective Marketplace Assignment cannot be greedily solved without causing sub-optimal allocations; it is solved via the Hungarian Algorithm (Kuhn-Munkres) in $O(N^3)$.
  • Multi-Seat Quota Allocation is framed as a Network Flow Problem, where Edmonds-Karp Max-Flow and Min-Cut identify hiring capacity bottlenecks.
  • Minimum Team Staffing is recognized as NP-Hard; solved via Exact Bitmask DP for small $K$, and Greedy Set Cover logarithmic approximation for general universes.

Viva Defense Guide

Frequently Asked Faculty Viva Questions & Proofs

Model technical answers for viva examination at 2nd-year B.Tech DSA level.

Q1: How does KMP achieve O(N + M) time, and how does it differ from Rabin-Karp?

Answer: The Naive string search takes $O(N \times M)$ because upon a mismatch, the text pointer resets. KMP (Knuth-Morris-Pratt) preprocesses the pattern in $O(M)$ into a prefix function table $\pi[i]$, where $\pi[i]$ is the length of the longest proper prefix of $P[0..i]$ that is also a suffix. When a mismatch occurs at $P[j]$, instead of resetting, the pattern shifts to index $\pi[j-1]$, guaranteeing that characters in the text are never scanned backwards, achieving strict $O(N + M)$ deterministic time.

In contrast, Rabin-Karp computes a polynomial rolling hash: $$\text{hash}(S) = \sum_{i=0}^{m-1} S[i] \cdot B^{m-1-i} \pmod M$$ Updating the rolling hash for the next window takes $O(1)$ arithmetic time. Rabin-Karp runs in $O(N + M)$ average time but can degrade to $O(N \cdot M)$ on hash collisions, which is mitigated using a large prime modulus ($10^9 + 7$).

Q2: What is the recurrence relation for Levenshtein and Damerau-Levenshtein Distance?

Answer: For two strings $s_1$ and $s_2$ of lengths $m$ and $n$, $dp[i][j]$ stores the minimum edit operations to transform $s_1[0..i-1]$ to $s_2[0..j-1]$: $$dp[i][j] = \min \begin{cases} dp[i-1][j] + 1 & \text{(Deletion)} \\ dp[i][j-1] + 1 & \text{(Insertion)} \\ dp[i-1][j-1] + (s_1[i-1] == s_2[j-1] ? 0 : 1) & \text{(Substitution)} \end{cases}$$ In Damerau-Levenshtein, adjacent character transposition is supported: $$\text{If } i > 1, j > 1 \text{ and } s_1[i-1] == s_2[j-2] \text{ and } s_1[i-2] == s_2[j-1]:$$ $$dp[i][j] = \min(dp[i][j], dp[i-2][j-2] + 1)$$ This allows fixing single-step typing errors like "teh" $\to$ "the" or "jsavscript" $\to$ "javascript" with an edit distance of 1 rather than 2.

Q3: What is the fundamental difference between the Hungarian Algorithm and Network Flow?

Answer:

  • Hungarian Algorithm (Kuhn-Munkres): Solves the WEIGHTED 1-to-1 Assignment Problem. Given an $N \times M$ cost matrix ($\text{Cost} = 100 - \text{Score}$), it finds a perfect matching that minimizes total cost in $O(N^3)$ polynomial time. It operates on dual potential variables ($u_i, v_j$) satisfying $u_i + v_j \le c_{ij}$.
  • Network Flow (Edmonds-Karp): Solves CAPACITY-CONSTRAINED Feasibility Matching. Roles can have headcounts $> 1$ (multi-seat openings). Edges exist only if candidates meet a quality threshold. Furthermore, the Max-Flow Min-Cut Theorem allows us to identify the hiring bottleneck: the reachable set in the residual graph isolates exactly which roles are starving for talent.
Neither algorithm replaces the other; Hungarian is used for weighted bijective matching, while Network Flow is used for capacity allocation and bottleneck diagnosis.

Q4: Why is Minimum Set Cover NP-Hard, and why compare Exact Bitmask DP with Greedy Set Cover?

Answer: Minimum Set Cover is NP-Hard (reduction from Vertex Cover / 3-SAT). No polynomial-time exact algorithm is known unless $P = NP$.

In Talent Engine, we showcase both approaches:

  • Exact Bitmask DP (Module 3): Uses a state $dp[\text{mask}]$ representing the minimum team to cover skill bitmask $\text{mask}$. Running in $O(2^K \cdot N)$ time, it finds the mathematically optimal roster for small instances ($K \le 18$). When $K > 18$, the state space ($2^{18} = 262,144$) explodes exponentially, proving intractability.
  • Greedy Set Cover (Module 5): Iteratively selects the candidate offering the maximum marginal skill contribution to currently uncovered skills. Running in $O(|U| \cdot N)$ polynomial time, it guarantees a logarithmic approximation bound: $$H(|U|) = \sum_{i=1}^{|U|} \frac{1}{i} \le \ln |U| + 1$$ We do NOT claim Greedy is always optimal; it is a provably bounded polynomial approximation.

Q5: Why choose Randomized QuickSort over Deterministic QuickSort, and what is its complexity?

Answer:
• Expected Time Complexity: $O(N \log N)$
• Worst-Case Time Complexity: $O(N^2)$
• Auxiliary Space Complexity: $O(\log N)$ average call stack

Rationale: Deterministic QuickSort (picking first, last, or fixed index) degrades to $O(N^2)$ on already-sorted, reverse-sorted, or structured candidate score lists. By choosing the pivot index uniformly at random ($r \in [\text{low}, \text{high}]$), the probability that an adversary can force unbalanced $1$ vs $N-1$ splits across all partitions is infinitesimally small ($\sim 2^N / N! \to 0$).

Q6: How are Java Parallel Streams implemented, and what determines their performance?

Answer: Java Parallel Streams use the common ForkJoinPool.commonPool(), recursively splitting the dataset using Spliterator work-stealing queues across available hardware threads (Runtime.getRuntime().availableProcessors()).

Parallel performance is workload, dataset batch size, and CPU-core dependent. For trivial collections ($N < 50$), thread dispatch and join coordination overhead can outweigh computational gains. For large candidate batches or heavy string score computations, multi-core parallelism provides substantial throughput speedups. Our system includes an empirical live benchmark measuring both sequential and parallel execution times directly on the running JVM.
